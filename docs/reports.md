# Reports system

Read before touching `api/reports/`.

PDF generation uses `ReportsPdfService` backed by `ReportRenderer` (`src/api/reports/report-renderer.service.ts`). Templates are JSON files in `src/api/reports/templates/*.json` that declare pages, element types (`title`, `paragraph`, `table`, `image`), styles, and `{{variable}}` placeholders filled at render time. `renderTemplate()` streams a PDF to a response; `renderTemplateIntoDocument()` writes into an existing PDFKit doc for multi-template composition. `PdfService` (`src/common/pdf/pdf.service.ts`) is the shared PDFKit wrapper.

Report rows are built in `ReportsRepository.getReportRows` (`src/database/repository/reports/reports.repository.ts`): parameterized Drizzle SQL (no injection), with sortable columns whitelisted. `time_spent` is only populated when `plugins.itop_training` is enabled (see `docs/mail-moodle.md`). The `moodle_password` column shown in some templates (e.g. `dedication-v1.json`) is read plaintext (intentionally — see `docs/security.md`).

`POST /reports/export`'s `include_passwords` flag is restricted to ADMIN/MANAGER: `ReportsController.exportPdf` throws `ForbiddenException` if a VIEWER or TUTOR requests it (checked server-side, not just hidden client-side, since the endpoint itself is open to all four roles). The client also hides the "Incluir contraseñas" checkbox from non-ADMIN/MANAGER via `AuthzHide` (`reports.route.tsx`).

Filters are declared in `ReportFilterDTO` (`src/dto/reports/report-filter.dto.ts`). The WHERE clauses are built in `ReportsRepository.buildWhereConditions(filter, exclude?)` — a **pure** method (no DB access, unit-tested in `reports.repository.spec.ts`) shared by both the row listing and the facets. Among the filters, `bonified?: boolean` (UI checkbox "Solo bonificados" in `reports.route.tsx`) restricts rows to enrolments with `user_group.bonified = true` (the FUNDAE bonification flag — see `docs/user-merge.md`/`group-bonification.service`). Like the other filters, it is carried inside the export payload's nested filter, so it also constrains the generated PDF/Excel.

## Faceted filters (interdependent dropdowns)

The report dropdowns (Company, Center, Course, Group, Role, plus the course axes Modality, Client, Funding) are a **faceted search**: each one only offers values that still have a matching report row given the *other* active filters. Backed by `GET /reports/facets` → `ReportsService.getFacets` → `ReportsRepository.getReportFacets`, which runs 8 `SELECT DISTINCT` over the **same JOINs** as the listing (so e.g. a course "belongs to" a company only through that join chain). Modality/Client/Funding are multi-select enum filters (`courses.modality|client|funding`, `inArray` in `buildWhereConditions`) and their facets return the distinct enum values present (`{ value }` columns flattened to `string[]`).

- **Standard facets**: each dimension's options are computed with all filters *except its own* (`buildWhereConditions(filter, exclude)` with `exclude` ∈ `FacetDimension`), so a multi-select doesn't restrict itself and can still be widened. Global filters (dates, search, completion %, `bonified`) never get excluded.
- **Group** is only computed when a course is selected (otherwise an empty list), mirroring the client's `disabled={!selectedCourse}`.
- Client: `useReportFacetsQuery` (`client/src/hooks/api/reports/use-report-facets.query.ts`) is called with the filter params minus pagination/sort (`ReportFacetsParams`), uses `placeholderData: keepPreviousData`, and feeds every dropdown's `options`. On each recompute an effect in `reports.route.tsx` **auto-prunes** any selection no longer present in its facet (keeps filters/table coherent). `useReportRolesQuery` is kept only to apply the default "student" role on load.
- Note: the internal facet query builder is typed `any` and re-asserted per facet because a wide generic on `selectDistinct` breaks drizzle's join-chain inference.

## Sending Dedicación/Certificado by mail to a center (`POST /reports/send`)

Sibling of `/reports/export`: instead of streaming a PDF/ZIP, it emails the PDFs to whoever should stay informed about the selected students — **one email per group**, each containing only that group's own students. Row selection is shared with export (`ReportSendDTO` mirrors `ReportExportDTO`'s `filter`/`selected_keys`/`select_all_matching`/`deselected_keys`), via `ReportsService.resolveRows()` (extracted from the old duplicated logic in `exportPdfFromPayload` — both now call the same helper).

### Grouping: by petición, not by center

The whole point of this flow is "keep the requesting center's contact informed about their students" — so rows are grouped by the **`course_requests` (petición) that enrolled each student**, not by the student's current center. `ReportsMailService.buildSendGroups` (`reports-mail.service.ts`) resolves this per row:

1. For every distinct `id_group` in the resolved rows, `CourseRequestStudentRepository.findAssignedByGroups` fetches `{id_request, id_group, dni}` from `course_request_students` — mirrors the DNI-cross-reference `CourseRequestService` already uses for "en grupo/total" (`docs/course-requests.md`). DNI is normalized (`normalizeDni`) on both sides before matching, same as the rest of that module.
2. A row matches a petición when its `(id_group, normalizeDni(dni))` is found in that set. **Kind `'request'`**: grouped by `id_request` (`group_key = "req:<id_request>"`), default recipient = that petición's own `contact_email` (fetched via `CourseRequestRepository.findByIds`, batched).
3. Rows with no petición match (enrolled by hand, via Excel import, or synced from Moodle — never went through "Matricular → Desde Peticiones") fall back to grouping by the student's current `id_center`. **Kind `'center'`**: `group_key = "ctr:<id_center>"`, **no suggested recipient** — the operator has to type an email by hand. The client flags this in red ("Sin petición asociada") next to the center name so it isn't mistaken for a resolved petición.
4. Rows with **neither** a petición match **nor** a center at all are `unassignable` — there is nothing to email them to. They never become a group; they're only surfaced as a count (`unassignable_count` in the preview, a single synthesized `skipped` entry in the send result) so they're never silently dropped without a trace.
5. If two different peticiones happen to have assigned the same DNI to the same `id_group` (the known dedupe edge case in `docs/course-requests.md`), the most recent one (highest `id_request`) wins — last-write-wins while building the lookup map, rows ordered ascending by `id_request`.

- `POST /reports/send/groups` (plain `ReportExportDTO` body) resolves the selection to this grouped preview — `{groups: [{group_key, kind, center_name, course_name, student_count, eligible_count, suggested_email, row_keys, eligible_row_keys}], unassignable_count}` — with **no PDF/email side effect**. The client (`SendReportMailModal`) uses it directly to build the recipient-editing UI: no more per-row query, the suggestion arrives already resolved.
- `ReportsPdfService.buildDedicationPdfBuffer`/`buildCertificationPdfBuffer` (public — reused by both export and send) build the requested attachments (`attach: ('dedication'|'dedication_passwords'|'certification')[]`) per group, sent via `MailService.sendMail`'s `attachments` option (SMTP only — Moodle notifications don't support attachments, so this flow never offers "vía Moodle"). `dedication_passwords` is a **separate attachment**, not a modifier of `dedication` — both can be requested together, producing two distinct PDFs in the same email. Restricted to ADMIN/MANAGER (`ReportsController` throws `ForbiddenException` for VIEWER/TUTOR when `attach` includes it, same pattern as `/reports/export`'s `include_passwords`); the client hides the checkbox from those roles via `AuthzHide`.
- **Certificate rows are filtered to `completion_percentage >= 75` per group** before rendering; if nobody in a group is eligible, its certificate is skipped (noted in the result) but dedication (if requested) still goes out.
- **Recipients are resolved client-side, not guessed server-side**: the caller must pass `recipients: [{group_key, emails}]` — a group with no matching entry (or an empty `emails` list) is skipped, never silently dropped without a reason in the result.
- `POST /reports/send/test` sends a single copy (using the **first** group found in the selection) to an arbitrary `test_email`, real recipients untouched — same pattern as the student mail modals' "Enviar prueba".
- Template variables for this flow add `{NOMBRE_CENTRO}`; `{USUARIO_MOODLE}`/`{CLAVE_MOODLE}` resolve to empty (the recipient is a center/petición, not a Moodle user) — see `REPORT_MAIL_TEMPLATE_VARIABLES` client-side.
- Entry points: a "Enviar informe" button next to "Correo" in the group detail's `GroupUsersManager` (selection = the same checked students, keyed `id_user-id_group`), and a "Formación en el centro" tab in the center detail (`CenterTrainingTab`, a leaner purpose-built table reusing `useReportsQuery`/`useReportFacetsQuery` scoped to `id_center`, not the full `reports.route.tsx` — note this tab still *lists* students by their current center for browsing/selection; the send-time grouping by petición happens afterward, inside the modal). Both open the same `SendReportMailModal`.
- **Role: `ADMIN`/`MANAGER`/`TUTOR` only — no `VIEWER`**, unlike the rest of `/reports` (see `docs/security.md`'s "Roles" split). `POST /reports/send/groups`, `POST /reports/send`, `POST /reports/send/test` are all `RoleGuard([ADMIN, MANAGER, TUTOR])` server-side (note `/reports/export` itself stays open to `VIEWER` — only this send flow is restricted); the client mirrors it by hiding "Enviar informe" (`AuthzHide roles={[ADMIN, MANAGER, TUTOR]}`, separate from "Correo") and by omitting the "Formación en el centro" tab entirely for `VIEWER`.
